# CI dependency repairs — 2026-10-04

The published workflow exposed two dependency failures before image scanning:

- `trivy-action@0.33.1` was not an existing tag. Pinning the official v0.33.1 commit resolved action discovery, but its default Trivy v0.65.0 release then returned HTTP 404.
- CI now pins the official [trivy-action v0.36.0](https://github.com/aquasecurity/trivy-action/releases/tag/v0.36.0) commit and explicitly selects the available [Trivy v0.70.0 release](https://github.com/aquasecurity/trivy/releases/tag/v0.70.0). The HIGH/CRITICAL failure threshold remains enabled. SARIF is also retained as a downloadable artifact, including when scanning finds a vulnerability; upload steps run only when a report exists.

Gitleaks separately mistook ten SHA-256 values in historical source manifests for credentials. `.gitleaksignore` records only those exact commit/path/rule/line fingerprints. Gitleaks 8.24.3 passed a full-history scan after review. Two temporary negative controls, including a credential in the same manifest path, both remained detectable. No path-wide exclusion was introduced.

These repairs do not change the owner-supplied cloud benchmark results in the README. Subsequent workflow runs provide their own CI evidence.

## Findings from the restored scanner

The first successful scan execution found HIGH advisories in Jackson core/databind 2.21.5 and 3.1.5. Both BOMs now use the scanner-recommended patched releases within the same minor line: 2.21.7 and 3.1.7. No vulnerability exception was added; the image scan still fails on HIGH/CRITICAL findings.

The GitHub code-scanning API returned `403: Code scanning is not enabled for this repository`. The mandatory downloadable `image-scan` artifact therefore serves as the report destination for this private repository. Optional Security-tab publication is enabled for public repositories, or after enabling code scanning and setting the repository variable `CODE_SCANNING_ENABLED=true`. Its required `actions: read` permission is explicit. The reporting destination does not affect the scanner's exit status or severity gate.

The patched image's next SARIF contained zero HIGH/CRITICAL findings and three MEDIUM entries (LZ4 and OpenTelemetry). The action nevertheless exited with failure because its SARIF default scans all severities even when `severity` is supplied. Setting its documented `limit-severities-for-sarif: true` makes the declared HIGH/CRITICAL threshold effective. This does not claim that the image has no lower-severity findings; the complete pre-filter report remains attached to workflow run `37177819221`.

Local patch validation passed all 56 JUnit tests across 21 suites without failures or skips, plus Checkstyle and SpotBugs. Maven's effective POM resolves both patched BOMs; a forced local JAR rebuild also confirmed all four core/databind JARs are at 2.21.7 or 3.1.7.
